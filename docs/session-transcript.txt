❯ /speckit-constitution Python 3.12 managed with uv. FastAPI for the HTTP       
  layer. Google Gemini via the google-genai SDK is the only runtime LLM         
  provider. Plain Python orchestration with direct function calls between       
  agents; no agent frameworks. The Router is the primary entry point: it runs   
  the guardrails, then returns an ordered list of steps and the user's language 
  as en or pt; the orchestrator runs that sequence and passes each agent's      
  output to the next. Every answer passes through a final Personality step that 
  applies the brand voice in the language given by the Router and may not add   
  facts; sources are attached by code after it; if it fails, the agent draft is 
  returned; deterministic refusals skip it. Each agent's prompt lives in a      
  dedicated module and states role, scope, output format and refusal rules. The 
  current date is injected by code into agent prompts. Right model per task,    
  chosen and justified, never the cheapest or the most expensive by default:    
  routing and input classification use GEMINI_ROUTER_MODEL with thinking level  
  minimal; the Personality step uses GEMINI_PERSONALITY_MODEL with thinking     
  level minimal; answering agents use GEMINI_MODEL with thinking level low;     
  embeddings use GEMINI_EMBEDDING_MODEL; all model names and thinking levels    
  come from environment variables. Every LLM call goes through one client       
  wrapper that records model, latency_ms, prompt, output and thinking tokens    
  from usage_metadata, computes cost in USD from a price table configured via   
  environment variables, including Google Search requests counted from          
  grounding metadata because they are not part of usage_metadata, logs it as    
  structured JSON with the request_id, and enforces a per-request token budget; 
  thinking tokens are billed as output, so cost is controlled by thinking       
  level, not by shrinking max_output_tokens. The wrapper preserves the complete 
  model content, including thought signatures, across tool-calling turns.       
  Google Search grounding and function calling run in separate LLM calls, never 
  in the same request. Every API response returns the route taken, sources,     
  and a trace with per-agent model, latency, tokens and cost, plus the request  
  total. Cost limits are explicit and configurable: max message length, top-k   
  retrieved chunks, max tool-call iterations per request, per-request token     
  budget. Guardrails run before routing and are deterministic first: message    
  length limit, masking of card numbers validated by Luhn and CPF before text   
  reaches any LLM or log, prompt-injection heuristics in English and            
  Portuguese. The user_id comes only from the request and is injected into      
  tools by code, never chosen by the LLM; tools return only that user's data.   
  Unsafe or out-of-scope requests get a polite refusal; when retrieval          
  similarity is below threshold or the answer cannot be grounded, the system    
  does not guess and hands off to a Human Escalation Agent that records a       
  ticket and returns its id. Vector search uses cosine space with similarity    
  defined as 1 minus distance. Domain answers must be grounded in retrieved     
  context and cite source URLs. Every LLM output that drives control flow is    
  parsed into a Pydantic model. Every tool returns a structured result and      
  handles its own failures. Every LLM call has a timeout and one retry on 429   
  or 5xx; when the budget is exceeded or the LLM stays unavailable, the API     
  still returns valid JSON and hands off. Retrieved content (RAG, web, tool     
  results) is untrusted data: delimited in prompts and never treated as         
  instructions. Evals are part of the product: evals/dataset.jsonl holds the    
  official scenarios plus adversarial cases (prompt injection, injection inside 
  retrieved content, card number in message, asking for another user's data,    
  out of scope), each with expected route and assertions; evals/run.py runs     
  them against the live API and writes evals/report.md with routing accuracy,   
  citation rate, correct refusal rate, p50 and p95 latency, and average cost    
  per request, and exits non-zero below configured thresholds so it works as a  
  regression gate. Every requirement has an ID (R1, R2...) and at least one     
  pytest test referencing it in its name; unit tests mock the LLM; integration  
  tests call the HTTP endpoint and run the full orchestration with the LLM      
  stubbed at the wrapper, asserting route, data flow between agents, user_id    
  injection, refusals and handoff. Secrets only via .env, with a committed      
  .env.example. The app runs with docker compose up and with plain docker build 
  and docker run. Simplicity over abstraction: build only what the spec and     
  this constitution ask for. Each SDD phase (constitution, spec, plan, tasks)   
  and each completed task gets its own commit on the repository default branch, 
  with no feature or docs branches, pushed immediately, so the remote history   
  proves the stages and their times. Scope of this phase: write the             
  constitution from this text only, with no web research and no API calls;      
  contracts get verified in the plan phase.

❯ /speckit-specify Build the multi-agent system described in docs/challenge.md, 
  following the constitution. The required workflow is the image                
  docs/agent-workflow.png: Input, Router, specialized agents with their tools,  
  Personality, Output; the custom agent is the Human Escalation Agent.          
  Knowledge base sources, both one level deep from their start page, same host  
  only, deduplicated by final URL and content hash, keeping only HTTP 200       
  text/html, max RAG_MAX_PAGES pages in total: site.getnet.com.br               
  (www.getnet.com.br redirects there; /duvidas/, /crediario/,                   
  /link-de-pagamento/, /pix/ and /todas-as-maquininhas/ must be included) and   
  www.getnet.net/en (/en paths only; /en/our-solutions/in-person-payments must  
  be included). The crawler is sequential, pauses 2 seconds between requests,   
  caches raw HTML under data/crawl_cache/, never refetches a cached URL unless  
  the refresh command is used, and stops crawling a host at the first 403 or    
  429. Text extraction must preserve tables, product cards and FAQ questions,   
  so it strips script, style, nav, header and footer plus text repeated in 30%  
  or more of the pages instead of relying on trafilatura main-content           
  detection. Chunk by heading and by FAQ question, not by fixed windows.        
  Retrieval combines vector top-k with lexical matching over a product alias    
  glossary, because users write in English while the main source is in          
  Portuguese: Get Clássica = Get Classic, Link de Pagamento = Payment Link,     
  antecipação = receivables advance, crediário, parcelas = installments.        
  Answers use the user's language and name the source; content from the global  
  site is not presented as confirmed for Brazil. Web search via Gemini Google   
  Search grounding for general factual questions like weather and exchange      
  rates. Refusals apply to unsafe or sensitive requests and to messages that    
  are not an information need, such as creative writing. Customer support tools 
  over simulated merchant data in a local JSON: get_receivables(user_id) for    
  settlement dates and amounts, get_terminal_status(user_id) for card machine   
  connectivity, last errors and suggested actions. All ten example scenarios in 
  the challenge are acceptance criteria, with assertions on the expected fact   
  for the five RAG scenarios. A compound message such as "When will yesterday's 
  sales be deposited and how does receivables advance work?" must run Support   
  then Knowledge. Each Router step names the agent and, for Knowledge, the      
  source: rag or web. The scenario "My card machine won't connect to the        
  internet, what should I do?" runs Support then Knowledge, combining terminal  
  status with the site's chip and connectivity steps; when a later step cannot  
  be grounded, earlier answers are kept and no handoff happens. Simulated data  
  covers cliente1988 and at least one other merchant and uses dates relative to 
  the current day, so "yesterday" always resolves; an unknown user_id gets a
